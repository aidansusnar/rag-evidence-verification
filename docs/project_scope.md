## 1. Project Overview

This project investigates whether adding an evidence-verification step to a Retrieval-Augmented Generation (RAG) system improves the reliability of answers generated from financial documents.

RAG combines information retrieval with large language models (LLMs) to generate responses grounded in external information. Although retrieving relevant documents can improve factual accuracy, RAG systems may still generate unsupported claims, misinterpret financial data, or perform calculations incorrectly.

The proposed experiment compares a baseline RAG system against an enhanced version that verifies generated answers against retrieved evidence before producing a final response.

The project will evaluate whether evidence verification improves answer correctness and factual support, while also measuring the additional computational costs associated with verification.

## 2. Research Question

**Primary Research Question:**

Does adding an evidence-verification step improve the reliability of retrieval-augmented generation when answering financial questions, and is the improvement worth the additional computational cost?

### Supporting Questions

1. Does evidence verification improve answer correctness compared with baseline RAG?
2. Does verification reduce unsupported or hallucinated claims?
3. How frequently does verification correctly identify unsupported answers?
4. Does verification introduce new errors or unnecessary abstentions?
5. How much additional latency and token usage does verification require?

## 3. Hypotheses

**H1 — Answer Reliability**

Evidence-verified RAG will produce fewer unsupported answers than baseline RAG.

**H2 — Answer Correctness**

Evidence verification may improve overall answer correctness by identifying and revising unsupported responses.

**H3 — Computational Overhead**

Evidence-verified RAG will require more inference time and tokens because it introduces additional LLM calls.

**H4 — Verification Limitations**

Evidence verification will not eliminate all errors and may incorrectly reject valid answers or introduce new mistakes during revision.

These are hypotheses to be tested, not established outcomes.

## 4. Dataset and Documents

The experiment will use FinanceBench, a financial question-answering benchmark developed by Patronus AI.

FinanceBench provides financial questions, reference answers, and supporting evidence from company financial reports.

### Initial Documents

| Document | PDF Pages | Benchmark Questions |
|---|---:|---:|
| AMD 2022 Form 10-K | 121 | 7 |
| PepsiCo 2022 Form 10-K | 503 | 5 |
| **Total** | **624** | **12** |

The initial experiment will use these 12 questions. Expanding to approximately 20 questions is an optional goal, depending on available time and technical progress.

### Dataset Handling

- Source PDFs will be processed locally using Python.
- FinanceBench questions will serve as evaluation inputs.
- Reference answers will be reserved for evaluation and will not be supplied to the generation or verification prompts.
- Retrieved evidence will come from the source financial documents.
- Original document names, page references, and question identifiers will be preserved.
- Source PDFs and benchmark files will remain excluded from GitHub until redistribution permissions have been reviewed.

## 5. Proposed System Architecture

Two systems will be compared under controlled conditions.

### System A — Baseline RAG

1. Receive a FinanceBench question.
2. Retrieve relevant passages from the corresponding financial report.
3. Provide the retrieved passages and question to an LLM.
4. Generate an answer with supporting source references.
5. Record the answer, retrieved passages, latency, and token usage.

### System B — Evidence-Verified RAG

1. Receive the same question and retrieved passages.
2. Start with the same initial answer generated by the baseline system.
3. Submit the answer and retrieved evidence to a separate verification step.
4. Determine whether the answer is supported by the retrieved evidence.
5. Accept the answer, revise it once, or abstain if adequate support is unavailable.
6. Record the final answer, verification decision, latency, and token usage.

### Experimental Controls

Both systems will use:

- The same financial documents.
- The same benchmark questions.
- The same document extraction and chunking approach.
- The same retrieved evidence for each question.
- The same generation model and initial generated answer.
- Consistent generation settings.

The primary experimental difference will be the additional evidence-verification process.

## 7. Connection to Cloud Computing

This project connects to Cloud Computing through data processing, remote inference services, and computational efficiency.

### Data Processing

The system will process financial documents through extraction, chunking, indexing, and retrieval stages.

These operations relate conceptually to the data-processing workflows studied through Hadoop, MapReduce, and Apache Spark.

Although the initial dataset is small enough for local Python processing, larger document collections could benefit from distributed preprocessing and indexing.

### Cloud-Based AI Services

The proposed RAG pipeline will use a cloud-hosted LLM through an API.

This allows the application to access remote inference resources without hosting a large language model locally.

### Computational Efficiency

The project will compare the additional computational overhead introduced by evidence verification.

Relevant measurements include:

- End-to-end response latency.
- Number of LLM API calls.
- Input and output token usage.
- Estimated API cost, when pricing information is available.

The goal is to examine whether reliability improvements justify the additional inference overhead.

Hadoop or Spark will not be incorporated solely for demonstration purposes. Their inclusion would require a clear technical or course-related justification.

## 8. Evaluation Criteria

The experiment will evaluate both systems using the same questions.

### Primary Metrics

**Answer Correctness**

Whether the generated response correctly answers the benchmark question when compared against the FinanceBench reference answer.

**Evidence Support**

Whether the claims in the generated answer are supported by the retrieved financial document passages.

### Secondary Metrics

**Abstention Rate**

The proportion of questions for which the system declines to provide a definitive answer.

**Verification Outcomes**

The number of answers accepted, revised, or rejected by the verification process.

**Response Latency**

The time required to produce each final answer.

**Token Usage**

The number of input and output tokens consumed during generation and verification.

**Estimated API Cost**

The approximate monetary cost of inference, based on recorded usage and applicable model pricing.

### Error Analysis

Errors may be categorized as:

- Retrieval failures.
- Unsupported factual claims.
- Numerical or calculation errors.
- Misinterpretation of retrieved evidence.
- Incorrect verification decisions.
- Revision-induced errors.
- Unnecessary abstentions.

Correctness and evidence support will be evaluated separately because an answer may be factually correct without being supported by the retrieved passages.

Given the small sample size, results will be interpreted as exploratory rather than statistically conclusive.

## 12. Risks and Limitations

**Small Sample Size**

The initial 12-question sample limits the generalizability of findings.

**PDF Extraction Quality**

Financial tables, unusual formatting, and page structures may affect retrieval accuracy.

**Retrieval Limitations**

A correct answer may be unavailable if the relevant evidence is not retrieved.

**Verification Reliability**

An LLM-based verifier may incorrectly accept unsupported claims or reject valid answers.

**Model Variability**

LLM outputs may vary across requests, even with consistent settings.

**Cost and Time Constraints**

API usage and implementation complexity must remain within the available course timeline and budget.

**Benchmark Leakage**

Reference answers and annotated evidence must not be unintentionally provided to the model during generation or verification.

**Course Requirements**

The final scope may need adjustment after reviewing the complete PRWd informational page and grading criteria.

## 13. Minimum Viable Project

The minimum successful implementation will:

1. Process the two selected financial reports.
2. Answer the same 12 FinanceBench questions using baseline RAG.
3. Apply a separate evidence-verification step to the baseline answers.
4. Compare correctness and evidence support.
5. Record latency, token usage, and abstentions.
6. Summarize the results and limitations in the final paper.

If implementation time becomes limited, optional expansion will be removed before reducing the quality of the core comparison.
